# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Purpose

This repository is the **`gvt-fleet` plugin** for Claude Code. It ships one skill, `/gvt-fleet:coach`, the coach's entry point for the gvt-fleet multi-repo coordinator. The skill runs only in a session started at the root of a gvt-fleet workspace. It runs the CLI that the plugin ships, `plugin/cli/bin/gvt-fleet.mjs`, with `--workspace` set to that folder (#58). It depends on the `gvt-dev` plugin. The plugin is published through the `claude-code-gvt-marketplace` catalog (marketplace name `gvt-plugins`).

This repository also holds the source of the gvt-fleet CLI, its tests, its CI and its command reference, imported from the workspace repository at the tag `cli-source-moved` (#82, decision record 0023). The plugin ships the CLI from `plugin/cli/` and its session hooks from `plugin/hooks/hooks.json`. The rules for changing the CLI start at "Developing the CLI" below.

## Validate

`commands.validate` in `.gvt-agent.json` is the validation command. It runs the leak guard, `claude plugin validate plugin`, the syntax check `node --check plugin/cli/bin/gvt-fleet.mjs`, and then the CLI test suite with `GVT_FLEET_FAKE_ONLY=1`. `commands.test` runs the suite alone. Run `commands.validate` before every commit, except the release commit (see "Releases", step 3). The suite reads the wiki, `README.md` and `CLAUDE.md` too (`test/wiki.test.mjs`), so a docs-only commit runs it as well.

In a worktree-isolated session, run the four parts as four Bash calls: `bash .github/scripts/leak-guard.sh`, `claude plugin validate plugin`, `node --check plugin/cli/bin/gvt-fleet.mjs`, then the suite (`commands.test`). The worktree guard refuses the chained command when it also reads the exit code (`; echo rc=$?`). Observed on #38. `claude plugin validate plugin` prints an `ICON_MISSING` warning, because the plugin has no icon. The warning does not change the result: read the last line, `✔ Validation passed`.

## Conventions

- **Commits:** `<scope>: <description>`.
- **Branches:** kebab-case.
- **Merges:** squash merge only.
- **Tags:** `v<semver>`, annotated, and equal to the `version` in `plugin.json`.
- **Changelog:** each new invocable skill adds an entry under `[Unreleased]` in `plugin/CHANGELOG.md` and needs a version bump at release. So does a contract bump (see "Coordinator contract"). An issue that proposes "a skill" says whether it means a new invocable skill or a mode of `/gvt-fleet:coach`. A new skill has a changelog entry, a version bump and a short noun as its name, and it changes the README sentence that says the plugin provides one skill. Observed in triage on #34: "a wrap skill" could mean either, and the coach left the choice to the plan (#37, #38). A change to the shipped CLI or hooks (`plugin/cli/`, `plugin/hooks/`) that a consumer can see, such as its output, its behaviour or its hook events, also adds an entry in the same pull request, because the plugin ships the CLI (#82). Observed at the v0.7.0 release: #111 changed the text output of `ready` and merged with no entry, and the entry was added in the release commit.
- **License:** MIT-0.
- **No machine paths and no private names** in any file. `.github/scripts/leak-guard.sh` enforces this. Read the script for the blocked names, and do not copy them into a file. The rule also holds for issue and pull request titles and bodies, which no check reads. Observed in triage on #45: the title as filed named the private workspace repository, as did the body. This repository is public and the workspace repository is private. A reader without access to a private repository cannot follow a reference to it, so the reference only confuses. A body that depends on a workspace issue describes it in prose, and the workspace issue links back to this repository. Observed in triage on #29: the split issue #30 is blocked by a workspace issue and names it only in prose. When a body names a private repository, rewrite it in prose. GitHub keeps the earlier revision in the body's edit history. Leave that revision there: the rule is about what a reader sees, not about confidentiality.
- **README:** `README.md` summarises what the overview and each mode show. A change to what they show also updates that summary, in the same commit. No check ties the two together. Observed on #7: the overview changed, and only the code review found the stale README sentence.
- **Skill names** are short nouns.
- **Plugin variables in a skill:** Claude Code replaces every `${CLAUDE_PLUGIN_ROOT}` in a plugin skill with the plugin's install folder when the skill loads, in the markdown and in the Bash rules of `allowed-tools` (the Claude Code skills documentation, "Available string substitutions", quoted on #58; not tested in a session). The Bash tool's environment does not carry the variable. So a sentence in `SKILL.md` that explains the variable does not name it: after the substitution, the coach reads a folder where the text means the variable. Describe it by its role instead, for example "the script path names the folder where this plugin is installed". Observed on #58: the first draft of the "Command form" paragraph named the variable twice.
- **Which coach:** `plugin/skills/coach/SKILL.md` calls the person who runs the skill "the coach". The composed dispatch prompt, the worker process ("Worker branches" below) and the issue comments call the coach session "the coach" and the person "the user". A sentence about who merges, approves or answers says which one it means. The user merges each side pull request, because GitHub refuses an approval from a pull request's author and the workers push under the user's account. Observed on #37: the issue comment's split ("the user merges each side pull request; the coach merges only the final pull request") used "the coach" for the session, while SKILL.md uses it for the person, so the section of SKILL.md that holds the prompt had to define both words.
- **Wiki:** a change to a page under `wiki/` adds a dated entry to `wiki/log.md`, as `wiki/schema.md` requires. A new page opens with OKF frontmatter whose `title` is its H1, and gets an entry in `wiki/index.md` (a new decision record in `wiki/decisions/index.md`). Run the `maintain-wiki` lint after a change to the page set.
- **Decision records** go in `wiki/decisions/`, numbered `NNNN-kebab-title.md`. Records 0001 to 0023 came with the gvt-fleet CLI from the workspace repository and keep their numbers (#82). This plugin's own first record, once 0001, is 0024. The next record takes the next free number. An issue body does not write the number of a record it proposes. It says "a decision record of this plugin", and the record takes the next free number when it is written. A literal goes stale when another record lands while the issue is open, as for the contract number (see "Coordinator contract"). Observed in triage on #18: the body proposed `0002`.

## Worker branches

A worker session on an issue of this repository uses one integration branch (the process of #34):

- The worker commits on side branches cut from its worktree branch. Each side branch gets a pull request into the integration branch, with no closing keyword. The coach reviews it. The user merges it, and that merge is the approval: GitHub refuses an approval from the author of a pull request, and the workers push under the user's account. The worker never merges a side pull request.
- After it opens a side pull request, the worker starts a background command that polls `gh pr view <n> --json state` about once a minute and ends at `MERGED` or `CLOSED`, tells the coach the number in its last message, and waits. The end of the poll starts the worker's next turn. When the user tells the coach that the pull request merged, the coach session also sends the worker a message (the merge notice of the coach skill), so a poll that did not start or that stopped does not leave the worker idle (#193). Observed on #193: the coach's message for the side pull request #195 reached the worker's background session while its poll was still between two checks, so the worker stopped the poll before it fast-forwarded. On 2026-11-27, a Bash call with `run_in_background` ran this poll in a worktree-isolated session, and its exit started a new turn: `until s=$(gh pr view <n> --repo <owner/name> --json state --jq .state); [ "$s" = MERGED ] || [ "$s" = CLOSED ]; do sleep 60; done; echo "state=$s"`. The `gh event listen` command that `gh pr create` suggests fails on this account with `HTTP 403: Event subscriptions are not enabled for this account`. Observed on #86. `gh pr checks <n> --watch` started just after `gh pr create` can exit 1 with `no checks reported` before any check has registered. Start the watch only after `gh pr checks <n>` lists at least one check, and read the last lines of its output: `no checks reported` is not a result. Observed at the v0.7.0 release, on #186.
- When the issue is done, the worker runs `gvt-dev:run-retro` and puts each proposal to the user. The approved proposals are one more side branch, with a side pull request. After it merges, or when the user approves no proposal, the worker waits for the coach before its finish turn, and says which of the two applies. Observed on #193: one of three workers opened its final pull request with no retro, and its session had to be respawned to run it.
- Only the final pull request, from the integration branch into `main`, carries the closing keyword. In the finish turn, the worker checks that the retro is done and reports which of the two cases applies, opens the final pull request, and does not merge it. The coach merges it.
- An edit of an issue or pull request text that names something only the integration branch has, such as a new decision record number, waits for the finish turn. Until then `main` does not have it, and the tracker would cite a file or number that a reader of `main` cannot find. Observed on #82: the new number of the record that was 0001 waits for the finish turn before it goes into the title and body of #25.
- At the finish turn, `git branch --merged` does not show that a side branch is merged, because side pull requests are squash-merged: the side branch's commits never reach the integration branch. Check each side pull request with `gh pr view <n> --json state,baseRefName,mergedAt` (state `MERGED`, base the integration branch). Then check its content with `git diff <side branch> HEAD -- <the files it changed>`, which prints nothing when the integration branch holds the work. Observed on #111: `git branch --merged` listed nothing for the merged side pull request #162.

The coach skill passes this process to the worker in its composed dispatch prompt ("The composed prompt" in `plugin/skills/coach/SKILL.md`) when the coach gives no prompt. The CLI's default dispatch prompt asks only for a closing keyword, and it does not replace this process. Observed on #33: the worker opened its first pull request straight into `main`, the user merged it, and the integration branch and the retro came afterwards.

## Releases

A release follows the skill `gvt-dev:release-plugin`, through the worker process above. The release commit does not go straight to `main`:

1. Compare `GVT_DEV_REF` in `.github/workflows/ci.yml` with the newest gvt-dev tag: `git ls-remote --tags --refs --sort=-v:refname https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev.git "v*" | head -1`. The `--sort=-v:refname` puts `v4.49.0` before `v4.5.0`. The tag list of the GitHub API does not promise a version order. When the two differ, bump `GVT_DEV_REF` first, on its own side branch (see "Run tests and validate").
2. List the shipped changes since the last tag: `git log --oneline <last tag>..origin/main -- plugin/cli plugin/hooks plugin/skills`. Compare the list with `[Unreleased]` in `plugin/CHANGELOG.md`, and add an entry for each change a consumer can see that has none.
3. On a side branch, set `version` in `plugin/.claude-plugin/plugin.json` and move `[Unreleased]` to a dated section. The commit subject is `release: vX.Y.Z`. This commit changes only those two files, so it gates on the first three parts of `commands.validate` (the leak guard, `claude plugin validate plugin` and `node --check plugin/cli/bin/gvt-fleet.mjs`). The full suite runs in CI on the side pull request, and the coach reads those checks before the merge. Observed at the v0.8.0 release: the local suite took 342 s, and CI then ran the same suite on the side pull request.
4. The final pull request merges the integration branch into `main`. Its squash commit on `main` is the commit to tag.
5. When CI on `main` is green, push the annotated tag `vX.Y.Z` on that commit.
6. Change only the `ref` of `gvt-fleet` in the marketplace catalog to `vX.Y.Z`.

There is no rebuild step: `plugin/cli/` is the CLI source, not a copy. Steps 4 to 6 write outside the pull request flow, so each one waits for the coach's yes. Observed at the v0.7.0 release.

## Coordinator contract

The skill pins the `coach.contract` number that the gvt-fleet CLI reports (`COACH_CONTRACT` in `plugin/cli/lib/dispatch.mjs`). A change that raises that number updates the skill in the same pull request.

The skill reads the keys in the CLI's contract table (`wiki/coordinator/coach-skill-contract.md` in this repository). Sometimes the skill needs a result key that the table does not list for that command. Then:

- The skill reads the key and treats a missing key as "not reported", as for any key.
- The skill's own contract table lists the key.
- The same change lists the key in `wiki/coordinator/coach-skill-contract.md` and pins it in `test/coach-contract.test.mjs` (see "Docs follow behaviour"). Adding a key does not raise the contract number (decision record 0008).

Observed on #6: the `wrap` result carries `branchRecord`, which the skill needs for rule 5, but the CLI's `wrap` row did not list it.

The reverse case: the skill stops reading a key. Then:

- The skill's own contract table drops the key.
- The same change drops the key from `wiki/coordinator/coach-skill-contract.md`. The CLI output does not change, so the skill's change does not raise the contract number.

A new value of a key that the skill reads, such as a new `reason` on a `needs-you` line, does not raise the contract number when an older skill still shows the line correctly. The skill names the value, and the contract page says when it appears, in the same change. Observed on #178: `watch` added the reason `agents:done`, and the contract number did not change.

An issue that makes a key meaningless says whether the skill keeps reading it. When an issue follows a decision record of the CLI, read that record before the change: it can say what happens to a key. Observed on #29: the skill stopped reading `now[].conflict`, which is always `false` since the class moved to the project Iteration field. The workspace decision record had already said that the key stays. It was read only after the merge, and the CLI's table still listed the key.

A CLI change that the skill adopts can also make `wiki/issue-triage.md` stale, for example its Class section and its "Set coordinator class" recipe. An issue that adopts such a change names both files. No check compares the triage contract with the CLI. Observed in triage on #29: the body named only `SKILL.md`, and the triage contract still said that labels keep the class (fixed in #31).

An issue body says whether its change raises the contract number. It does not write the number as a literal. A literal goes stale when the CLI raises the number while the issue is open. Observed in triage on #7 and #8: both said the number "stays 1" while the skill already pinned 2.

An issue that asks the skill to read a key names the results after which the skill reads it. Take that set from the command reference, which says on which results the key is present. Observed in triage on #22: the body read `checkedOutBranch` only after `wrapped`, while the reference says the key is always present on a `wrap` result, so a `branch-kept` result can also report a kept branch.

An acceptance row that pledges "the contract number does not change" checks the branch diff, not the number. It compares the contract fragments on the removed lines with those on the added lines:

```
git diff origin/main...HEAD -- plugin/skills/coach/SKILL.md | grep -E '^-[^-]' | grep -o -E 'contract[^|]{0,6}[0-9]+'
git diff origin/main...HEAD -- plugin/skills/coach/SKILL.md | grep -E '^[+][^+]' | grep -o -E 'contract[^|]{0,6}[0-9]+'
```

The number is unchanged when both commands print the same lines, or nothing. Controls, over one commit each (`git diff <c>~1 <c> -- plugin/skills/coach/SKILL.md | …`):

| Commit | Removed lines | Added lines |
|---|---|---|
| `f841961`, which raised the number | `contract 1`, `contract: 1` | `contract 2`, `contract: 2` |
| `e664c32`, a path fix on the line that holds the number | `contract: 2` | `contract: 2` |

A commit that adds a new mention of the current number also prints a difference. Read the diff in that case.

An earlier form of this check counted the added and removed lines that pair `contract` with a digit, and expected 0. It counts a changed line, not a changed number. Observed on #15: the path fix in `e664c32` made it print 2 while the number stayed the same.

Every sentence in SKILL.md about what a CLI command returns or does has a source in the command reference of this repository. `wiki/coordinator.md` is its index, and each command's section is in a file under `wiki/coordinator/` (for example `wiki/coordinator/workers.md` for `status` and `watch`). Read them in your worktree, after a `git merge origin/main` or on a branch cut from a fresh `origin/main`. Do not read them from a checkout of the workspace repository: its copy is frozen at the tag `cli-source-moved`, and it was written for paths that no longer match SKILL.md. Observed on #8, before the move: a local checkout of the workspace still had the reference as one `docs/coordinator.md` of 944 lines, while `main` had split it into an index and ten files. When the reference is silent, read the CLI code (`plugin/cli/`). When the code is silent too, leave the sentence out. No test compares SKILL.md with the CLI. Observed on #7: the code review found three sentences that said more than the reference. One had no source at all (the exit code of an older CLI for `--class`). One was true only by the CLI code (`class` removes the other label of an issue that carries both). One attached a half-way state to the wrong result.

A change that touches several command groups reads every file under `wiki/coordinator/`, not one. Observed on #4. The files are in this repository, so the Read and Grep tools reach them; a brief to an agent with no Write tool, such as `gvt-dev:issue-triage-analyst`, names the files to read.

Readiness is not described under `wiki/coordinator/`. The ready set and its dependencies (sub-issues, `Blocked by` links, `Depends on` text) are in `wiki/design.md`, under "Ready set". A sentence that says `dispatch` refuses an issue that is not ready has two sources: step 2 of `dispatch` runs `claim` (`wiki/coordinator/workers.md`), and `claim` runs the readiness check again on fresh data (`wiki/coordinator/claims.md`). Observed on #62: `wiki/coordinator.md` and nine pages under `wiki/coordinator/` were read, and none of them names a sub-issue or a `Blocked by` link. Only `design.md` does.

A skill step that reads GitHub with `gh` directly, not through the CLI, has no source in the command reference. Probe each `--json` field that the step reads once, live and read-only, and say in the skill what it does when an older `gh` rejects the field. Observed on #62: the link check reads `gh issue view --json parent`, probed on `gh` 2.105.0 against a known sub-issue. With an older `gh`, the skill runs the call again without `parent` and says that siblings were not checked.

An issue body's command syntax and ordering are proposals. The command reference on `main` decides. When they differ, follow the reference and say so in the pull request. The `--json` output can have another shape than the text output. For example, the text output of `status` sorts issue workers and task workers into one list, but `status --json` keeps them in two arrays, `workers` and `tasks`. Observed on #4: the body wrote the task name as optional (`[name]`), while `dispatch --task` requires the slug, and it asked for task rows "in the order `status` gives", which the JSON does not define across the two arrays.

A contract bump is a breaking change for consumers:

- The `[Unreleased]` section of `plugin/CHANGELOG.md` gets a `Changed` entry with a **Consumers** note that names the contract number the plugin needs.
- The release bumps at least the minor version.
- The CLI and the skill ship in the same plugin release, and the skill runs the plugin's copy of the CLI (#58), so the skill and the CLI it runs move to the new number together. Releases up to v0.6.0 ran the workspace's own copy, which could report an older number.

## Developing the CLI

The sections from "Run tests and validate" to "Safety rules for the code and its probes" are the rules for changing the gvt-fleet CLI. They come from the `CLAUDE.md` of the fleet workspace's repository, where the CLI was developed until decision record 0023 moved it here (#82), with the names of the private organization, its repositories, the user and the machine's folders replaced by descriptions. In them, a bare `#N` and a "PR #N" cite an issue or pull request of the workspace's repository, unless the text names this repository. The wiki, records 0001 to 0023 included, writes such a reference as "workspace #N", so that a bare `#N` in a wiki page names an issue of this repository (#86).

`<workspace>` is the folder of a fleet workspace, which holds `config/`, `state/` and `repos/`. "The main checkout" is the workspace's own checkout. A worktree of this repository sits inside the coach's workspace (`<workspace>/repos/<owner>/<name>/.claude/worktrees/<name>`), and `plugin/cli/` holds no `config/`. So a CLI run from a worktree with no `--workspace` takes the outermost workspace at or above the current folder (`findWorkspace` in `plugin/cli/lib/workspace.mjs`), that is the live workspace, and without `--state-dir` it uses the live state.

## Run tests and validate

Use Git Bash. Set `GVT_FLEET_FAKE_ONLY=1` so that no test can reach the real `gh` or `claude`.

```
GVT_FLEET_FAKE_ONLY=1 node --test "test/*.test.mjs"
```

The commands are in `.gvt-agent.json`. `test` runs the suite. `validate` runs the leak guard, `claude plugin validate plugin`, `node --check plugin/cli/bin/gvt-fleet.mjs` and then the tests with `GVT_FLEET_FAKE_ONLY=1` set inline, so it needs a POSIX shell (Git Bash).

CI (`.github/workflows/ci.yml`) runs the syntax check and the tests on `windows-latest` with Node 24 and Git Bash, for every pull request and every push to `main`. It sets `core.autocrlf false` before checkout so the fixtures keep LF, and it fails when no test passed. `.github/workflows/leak-guard.yml` runs the leak guard.

The CI runner has 2 cores (`availableParallelism=2` in the "Show versions" step), so node's default `--test-concurrency` of cores minus one ran the files one at a time. The tests are CPU-bound on starting git and node processes: at 4 files at once on one runner, each test took about 2.8 times as long and the step saved only about 30% (#76). So CI splits the suite into three shards, one runner each, with `--test-concurrency=2`, and a `validate` job reports whether every shard passed. `scripts/ci-shard.mjs list <k> 3` picks each shard's files by their time in `scripts/shard-times.json`: longest first, each to the shard with the least time so far; a file with no recorded time counts as the median. node's own `--test-shard` gives file *i* of the sorted list to shard `(i mod 3) + 1`, so the heavy files stacked by name and every new test file reshuffled them: on 2026-11-20 one shard took 2m22s and another 4m08s (#157). When the shard times drift apart, refresh the times file from one or more CI runs (`gh run download <run id> --dir <folder>`, then `node scripts/ci-shard.mjs times <folder>...`) and commit it. The `R212` tests fail when the recorded times leave a shard more than 15% above the lightest, or name a test file that is gone. A whole file goes to one shard, so one slow file still sets a floor.

Do not judge a shard split by comparing job times across CI runs. The runners differ: on 2026-11-20 the same suite took 875 s of test time on one run and 1018 s on another, and a single file varied by up to a third (`worktrees-merged` 53 s and 83 s). Apply both splits to the per-file times of the same run instead. The shard times of the first run with the time-based split read as "no better" (4m18s on its slowest shard), while on that run's own times the split took 16% off the heaviest shard. Keep each git-sandbox test file to about 30 to 60 s of CI test time: `worktrees*.test.mjs` and `wrap*.test.mjs` were split for this, and their shared setup lives in `test/helpers/worktrees-shared.mjs` and `test/helpers/wrap-shared.mjs`. Each shard uploads its TAP output (`tests-tap-<shard>`), which gives each test's `duration_ms`.

The coordinator imports the issue-reference grammar from the installed gvt-dev plugin (`plugin/cli/lib/plugin-path.mjs`, found through `~/.claude/plugins/installed_plugins.json`). A machine without Claude Code needs `GVT_DEV_ROOT` set to a gvt-dev `plugin/` folder. The CLI requires gvt-dev `GVT_DEV_MIN_VERSION` (4.45.0, the first release with the grammar) or later, read from the plugin's `.claude-plugin/plugin.json`, and stops with one line that names it (decision record 0020). On a `GVT_DEV_REF` bump, diff the grammar between the old and new tag; when the coordinator starts to rely on a change, raise `GVT_DEV_MIN_VERSION` in the same pull request. CI clones the tag named by `GVT_DEV_REF` in the workflow; bump it when the coordinator moves to a new gvt-dev version. A gvt-dev release is such a move: when gvt-dev ships a release, open the `GVT_DEV_REF` bump pull request in the same session, and take CI on that pull request as the proof. On 2026-11-16 the pin was still `v4.49.0` when gvt-dev 5.1.0 shipped, so the whole 5.0.0 cycle had passed without a bump (#135).

An unmatched glob gives rc=0 and `# pass 0`. A zero pass count is not a pass. Read the count.

Never pass a directory to `node --test`. Pass the glob.

The `validate` and `test` commands use node's default reporter, which prints the totals as `ℹ pass N`, not `# pass N`. A grep for `# pass` over that output matches nothing. Add `--test-reporter=tap` when a check greps for `# pass`, `# fail` or `^ok`.

Do not filter by title with `--test-name-pattern`. With the `"test/*.test.mjs"` glob it reports the file count as passes (`# tests 18`, `# pass 18`), even for a pattern that matches no title. Measured 2026-11-03 on Node v24.11.1. To check one test, save a full TAP run and grep it for that test's own line: `grep -c -E '^ok [0-9]+ - <title prefix>'`.

TAP writes a `#` in a test title as `\#` (`ok 12 - R195: … game-backend\#353 shape`), because a bare `#` starts a directive. A grep or a script that maps a TAP line back to its title in the source must unescape it, or the title matches nothing. Observed 2026-11-20 on #157: the shard-time script lost two 6 s tests this way until it unescaped `\#`.

A TAP file lists each test title twice: once on its `# Subtest:` line and once on its `ok N -` or `not ok N -` line. A title grep that is not anchored counts every test twice (observed 2026-11-04: 6 hits for 3 titles). Anchor every title check on `^ok [0-9]+ - `.

The acceptance blocks write fixed paths under `$TEMP` (for example `$TEMP/gvt-fleet-s1.tap`). Two graders that run them at once overwrite each other's files. Give each concurrent run its own folder: `TEMP=<private dir> bash <script>`. Put that folder outside `%LOCALAPPDATA%` (for example under the user's profile folder). On 2026-11-05 the one suite failure was an `EPERM` while deleting a test temp folder under the session scratchpad in AppData (`NF-proc`); the test passed three times alone and did not fail again once `TEMP` pointed outside AppData. One occurrence, so treat the cause as likely, not proven.

A full suite run is slow enough to matter. Five full runs in a row (a mutation harness) took more than the 600 s tool timeout. Run a multi-run check in the background. Do not start a validator or reviewer in the tree while it runs, because the harness writes mutated source files.

One full run took about 160 s of wall time at 315 tests (measured 2026-11-04), and 328 s at 462 tests with nothing else running (measured 2026-11-06). With other sessions running on the machine, a run of 479 tests took 663 s. Most of it is the git-sandbox tests (R20, R22, R23, R24), because each `git` and `node` process start costs about 50 to 150 ms on Windows.

Two full suite runs at the same time slow each other a lot. On 2026-11-05 the validator reported about 816 s for its run (reported by the validator, not timed separately) while the orchestrator's own run was going, against about 130 to 160 s for a run alone. Start one full run at a time. Do not repeat a full run that a validator is already making.

Other heavy work next to a full run has the same effect, a live `gvt-fleet sync` included. On 2026-11-06 the `R46` test in `test/json-scan.test.mjs` timed out once (`spawnSync … ETIMEDOUT`) while a live `sync` ran, and it then passed three times alone. Start the full run when nothing else heavy is running.

To check an acceptance criterion against the live cache from a worktree, use a copy of the state. The real `state/` (`<workspace>/state/`) is the cache that every session reads. Copy `cache.db`, `claims.db` and `now-pointers.json` (the recorded Now of each project, decision record 0022; absent until the first `iteration promote`) from there to a scratch folder. Then run this worktree's CLI with `--state-dir <scratch folder>`: for example `ready --all --json` before and after `sync`. This makes GitHub reads only and writes only the copy. The real cache changes on the next `sync` of the CLI that the workspace runs, after the change ships.

Also pass `--config <workspace>/config/repos.json`, the main checkout's config, and read it. Before a command that can write to GitHub, such as `class`, read the repo's `project` in that file. A copy of the state does not stop a GitHub write. Observed 2026-11-16 on #143: a worktree of the workspace's repository read its own committed config, which still named the private organization's project for the workspace's repository, the main checkout's named `GenvidTechnologies/1`, and a `class … now` that was expected to print `noop` added the issue to the wrong project. The item was deleted by hand.

Gate policy for a plan of several tasks: a task that changes no behaviour gates on `node --check plugin/cli/bin/gvt-fleet.mjs` and the test files it touches. A task that changes behaviour, and the final gate, run the full suite in the background.

A task that creates a test file also runs `test/names.test.mjs` in its gate. That test requires line 1 of every test file to set `GVT_FLEET_FAKE_ONLY`, and a gate that runs only the new file passes without it. Observed 2026-11-06 on #45: the commit that created `test/classes.test.mjs` passed its own gate and left the suite red for one commit.

The `dispatch` event holds `key`, `status`, `step`, `claim` and `rollback` (`reportDispatch` in `plugin/cli/lib/commands.mjs`). Observed 2026-11-10 on #79: the issue gave the `NF-log` event as the reason the tests change, and triage corrected it. Observed 2026-11-14 on #127: the analyst's claim that `wrap` passes after an earlier merged pull request held only for a squash or rebase merge (#128).

A change to the merge proof of `wrap` (`decideProof` in `plugin/cli/lib/merge-proof.mjs`, `safetyCheck` in `plugin/cli/lib/worktrees.mjs`, or `plugin/cli/lib/wrap.mjs`) also runs `test/coach-contract.test.mjs` in its targeted gate. Observed 2026-11-16 on #128: the targeted gate over the four `wrap*` files and `test/merge-proof.test.mjs` passed, and only the full suite found the R111 failure.

Before a behaviour commit, check that its new tests fail against the old code. Do it in a scratch copy, never in the worktree, because the index holds staged work:

1. Copy the staged tree with `git checkout-index -a --prefix=<scratch dir>/`. It reads the index and changes nothing.
2. Replace each changed `plugin/cli/lib/` or `plugin/cli/bin/` file in the copy with `git show HEAD:<file>`.
3. When a test file imports a name that the old code does not export, add a stub export of that name to the old file. Without it the file fails to load (`ERR_TEST_FAILURE`, "does not provide an export"), which is not the red of an assertion.
4. Run only the touched test files in the copy, with `TEMP` outside AppData.

A new test that passes there guards behaviour that already held; report it as such. Observed 2026-11-08 on #34: implementers reported no red run in 5 of 8 tasks. In one, their own check left the task rows in the old array, so 3 tests stayed green that fail against the real old code.

When an acceptance row pledges a red run, name each test as expected red or expected green when the row is written. A test that pins behaviour the old code already had is expected green. Observed 2026-11-09 on #52: AC2 said "each test fails against main", and a code-124 test could not, so the row was amended as defective.

Read which assertion failed, not only that the test failed. A new test that also asserts a new result key fails against the old code on that key alone. Such a failure is not a red of the behaviour: report the test as a guard of behaviour that already held. Observed 2026-11-09 on #60: four new tests failed against the old code only because `removalAttempts` was undefined there, and the implementer reported them as red.

The same holds for a new output file or key that a test reads before it reaches the step under test. Put the assertion on the behaviour first, and the reads of what is new after it. Observed 2026-11-22 on #202: the "promote twice on one day" test read the new `now-pointers.json` after the first promote, so against the old code it failed with `ENOENT` and never reached the second promote, which the old code refused. Moving the file reads after the second promote made the red the refusal itself.

Before you trust a test of a retry or recovery path, run the code under test against the real state that the first failure leaves. Use a `.mjs` probe in a scratch folder, and print what the code reads (for example `observe` and `git worktree list --porcelain`). Observed 2026-11-09 on #60: the test that held the folder with a child process passed, while the real partial-delete state (see "Windows rules the code depends on") made the retry refuse at its second attempt. A probe of `observe` on that state found it. Why the test did not reproduce the state was not measured.

Write the exit code into the TAP file, not to stdout: `node --test … > <file>.tap 2>&1; echo rc=$? >> <file>.tap`. The Bash tool can move a long command to the background even when the brief asks for a foreground run, and then the `rc=` line on stdout is lost. Observed three times on 2026-11-06 (#45): the implementer reports carried a pass count and no exit code.

An acceptance row that pledges the suite total states it as main's count plus the tests the branch adds, and the grader measures main's count at the final gate. Never pledge an absolute number. Parallel slices merge into main while a branch is open, so an absolute goes stale. Observed 2026-11-06 on #43: the row pledged at least 480 passes from a baseline of 458; #47 merged during the work, main's count became 465, and the row had to be amended. Count the branch's tests with `git diff origin/main...HEAD -- test/ | grep -c '^+test('`, and check that `^-test(` gives 0. A renamed title counts as one removal and one addition. When the branch renames tests, the `^-test(` count equals the number of renamed titles, and the row names them. Observed 2026-11-16 on #141: two R195 titles changed with the repository name they cite, and the count was 2.

The same holds for every literal that a parallel slice can move: the command count (`names.length, N)` in `test/cli.test.mjs`), the next decision record number, and the number of a step in a numbered list. Pledge "main's value plus this branch's change", read at the final gate. Observed 2026-11-08 on #45: a row pledged `names.length, 19)`, the `watch` command (#51) merged first, and the right value became 20. The record number moved twice (0008 to 0009 to 0010).

## Parallel branches

Several workers can run on this repository at the same time, each in its own worktree. Their branches collide on things that only one branch can own:

- the next decision record number in `wiki/decisions/`;
- the command count in `test/cli.test.mjs` (`names.length`);
- numbered steps in `wiki/coordinator.md`, such as the Consumer workflow;
- the next free requirement prefix for test titles (`R2xx:`).

Observed 2026-11-06 to 2026-11-08 (#38, #40, PR #54): while the branch was open, `main` took the records 0007 to 0010, the `watch` and `class` commands, two Consumer workflow steps, and the prefixes R120 to R126. The branch had written its own record as 0007, counted 19 commands, and used R120, R121, R123 and R124 for its own tests. It was rebased four times, and the record moved twice. Twice the command-count line merged with no conflict and the wrong value (see "Docs follow behaviour").

GitHub runs no `pull_request` workflow for a pull request that has merge conflicts. Such a PR shows an empty check list and no warning, and `gh pr view --json mergeable` can return `UNKNOWN`.

- Before the decision record commit, run `git fetch origin main` and `renumber-adrs --next` against `origin/main`, not only against the branch.
- An issue or pull request text written while the record's branch is open cites the record by its title, not its number. A renumber at the finish turn changes the file, not the text already posted on GitHub. Observed 2026-11-22 on #201: #202 took 0022 on its own branch while the issues of #201's migration plan were filed.
- Before choosing a test prefix, list the prefixes on `origin/main` as well as on the branch: `git grep -h -o -E "^test\('R[0-9]+:" origin/main -- test`.
- Before opening a pull request, and whenever one shows no checks, run `git merge-tree --write-tree --name-only origin/main HEAD`. Exit 1 lists the conflicting files. Run it again just before `gh pr create`, not only before the full suite: on 2026-11-18 (#142), `main` merged two docs pull requests during one 10-minute suite run, and the pull request opened with a conflict.
- A `wiki/log.md` conflict between entries under the same date heading resolves by keeping both entries, the newer first. It happened on every update of #142 from `main`.
- After the first push, bring `main` into the branch with `git merge origin/main`, not a rebase. Pushing a rebased branch needs a force-push. On 2026-11-18 (#142), a clean rebase after the push was reset to the pushed tip and redone as a merge.
- After a rebase or a merge of `main`, re-run the full suite and every pledged acceptance row that counts one of the items above. A suite total is pledged relative to main (see "Run tests and validate").
- A measured fact that a document on the branch cites (a count, a list of files, a "still to do") can go stale when another slice merges, with no conflict. After a rebase, read the commits that came in from `main` (`git log <old base>..origin/main`) and re-measure each such fact in the branch's decision record or docs. Observed 2026-11-17 on #35: #151 scrubbed the private names from the code and tests while record 0019 still cited 121 occurrences in 19 test files as work to do; the rebase conflicted only in `wiki/log.md`.
- List the prefixes on `origin/main` again just before the push, not only when you choose them. On 2026-11-13 (#105), #106 merged with `R196` while the branch used `R196` to `R200`; the branch's prefixes moved up by one and the issue's rows were amended.
- List them once more just before the merge. Two branches that add tests with the same prefix in different files merge with no conflict, and no test fails on a duplicate prefix. Observed 2026-11-17: #152 (#128) was checked free of `R203` before its push, a parallel pull request merged the private-name scan as `R203` before #152 merged, and main held two `R203` groups until a follow-up renumbered the #128 tests to `R205`.
- When both sides of a rebase append to the end of one file, resolve the conflict with `git merge-file --diff3 <main copy> <base copy> <branch copy>`, and remove the markers. A plain conflict block can leave a line that both sides share, such as a closing `});`, outside the markers, so joining the two sides drops one copy. Run `node --check` on the file and wait for it to pass before `git add` and `git rebase --continue`. Never send the check in the same parallel batch as those steps: a failed check does not stop the other calls. Observed 2026-11-13 on #105: the rebase continued on a test file that failed the syntax check.

## Docs follow behaviour

A change to what a command does also updates its entry in the `HELP` table in `plugin/cli/bin/gvt-fleet.mjs` and its section in the command reference (its group page in `wiki/coordinator/`), in the same commit. No test ties the help text or the reference to the code, so they drift silently. Observed 2026-11-03: the `clone` help said an existing clone is left alone while the code fetched and fast-forwarded it.

The command reference is `wiki/coordinator.md` (usage, global flags, exit codes, where state lives, the workflows, recovery, safety) and one page per command group in `wiki/coordinator/`. A new command goes on the page of its group. A new group gets its own page and a link in the Contents list of `wiki/coordinator.md`. The new page opens with frontmatter whose `title` is its H1 (the schema, `wiki/schema.md`, gives the keys), and it gets an entry in `wiki/coordinator/index.md` and a dated entry in `wiki/log.md`. `test/wiki.test.mjs` fails on a missing frontmatter block or index entry; no test checks the log. An update to an existing wiki page also adds a dated entry to `wiki/log.md` (`* **Update**: …`), as `wiki/schema.md` requires ("Append an entry to `<wikiDir>/log.md` either way"). A page's headings start at `#`, one level above the old single file, so the anchor slugs are the same as before the split (#14).

Links between the reference pages are relative, for example `workers.md#live-workers` or `../coordinator.md#global-flags`. Never start a link with `/`: GitHub resolves it against the repository root, not against the folder.

The `maintain-wiki` lint drops the `#fragment` and checks only that the file exists. `test/wiki.test.mjs` checks the anchors: every relative link in `wiki/`, `README.md` and `CLAUDE.md` must reach an existing file and, with a fragment, a heading slug on that page. It also rejects a link that starts with `/`, a page without frontmatter or whose `title` is not its H1 (a decision record's `title` without its `NNNN. `), and a page that no index lists. It cannot tell whether a heading that is gone was moved on purpose: a change that moves or renames a heading in the reference also runs the read-only checker `doccheck-14.mjs` from the Acceptance Criteria of #14 (with its correction 7, and `ENTRY`, `SUBDIR` and `INBOUND` set to the `wiki/` paths) against the old file, and reports its `lost` and `missing` counts. Observed 2026-11-10 on #14: the split rewrote 30 links that crossed a page boundary, and only that checker could show that all of them still resolved.

This holds when a plan gives the code and the docs to two implementers (`gvt-dev:ts-implementer` and `gvt-dev:tech-writer`). Each one stages its own files, and the orchestrator makes one commit with both sets of paths. A planner that splits a task by domain plans two dispatches, not two commits. Observed 2026-11-06 on #43: the plan split the `watch` command from its `wiki/coordinator.md` section, and the contract test from the contract section, into separate commits. The contract pair was merged by hand before commit; the command and its section landed one commit apart.

When the two implementers work at the same time, the docs implementer writes from the brief, not from the code. Before the commit, read each behavioural sentence it added to the command reference (`wiki/coordinator.md` and `wiki/coordinator/`) and to the `HELP` table, and check it against the staged code. Observed 2026-11-08 on #34: the review of the branch found five doc sentences that said more than the code did. Examples: "every task prompt ends with the rule" while `worktree create` did not add it, and "no stash entries" while the code checks only the stash entries of the worker's branches.

Before a doc or HELP text says that a command "refuses" or "fails", read the status and exit code the code returns (`plugin/cli/lib/commands.mjs`). For `install-hooks` and `trust`, a refusal writes nothing and exits 2, and a runtime failure exits 1; other commands use exit 1 for both (the "Exit codes" section of `wiki/coordinator.md`). Observed 2026-11-04 on #9: the docs called a dangling symbolic link "refused", while the write failed with exit 1.

Adding or removing a command also changes the command count in `test/cli.test.mjs` ("NF-cli: every subcommand prints its own help with --help" asserts `names.length` as a literal). The test fails until the count matches.

A rebase or merge can set that literal wrong with no conflict. When both branches add one command, both change `names.length, 18)` to `19)`. Git sees two identical edits, merges them cleanly, and leaves 19 where the right count is 20. After every rebase or merge that brings in a new command, count the `COMMANDS` entries (`grep -c -E "^  \['[a-z -]+', '" plugin/cli/bin/gvt-fleet.mjs`) and compare the count with the literal. Observed 2026-11-08 on #45, rebasing onto #51.

The default dispatch prompt (`defaultPrompt` in `plugin/cli/lib/dispatch.mjs`) is quoted word for word in the `HELP` text and in `wiki/coordinator/workers.md`, where it sits in one code span. Keep backticks out of the prompt: one backtick would end the span early. Observed 2026-11-11 on #79.

Removing, renaming, or changing the type or meaning of a JSON key that the coach skill reads (the table in "The coach skill contract", `wiki/coordinator/coach-skill-contract.md`) changes three things in the same commit: `test/coach-contract.test.mjs`, that page, and `COACH_CONTRACT` in `plugin/cli/lib/dispatch.mjs`, whose number goes up. Adding a key that the skill reads changes the test and the page in the same commit, and the number stays (decision record 0008). The skill treats a missing key as "not reported". The skill is `plugin/skills/coach/SKILL.md` in this repository, and no test compares it with the CLI (see "Coordinator contract").

`watchCommand` in `plugin/cli/lib/commands.mjs` builds each row field by field (`{key, state, reason, detail, since, …}`) before it calls `nextWaits`. A new row key from `joinWorkers` does not reach the `watch` output until it is added there too. Observed 2026-11-13 on #105: the `questions` key was missing from every `watch` line until a test failed.

## Test conventions

- Each title is a string literal that starts with the requirement prefix, for example `R14: ...`, `Q6: ...`, `NF-...: ...`. This lets a grep find the test for a requirement.
- Use top-level `test()`. Do not use `describe`.
- Do not add skip guards. A test that cannot run must fail.
- Put fakes at the `gh` and `claude` boundary (`test/fakes/`). Do not fake inside the logic.
- `plugin/cli/bin/`, `plugin/cli/lib/` and `test/` name no private organization, repository, person or machine path, because this repository is public. Use generic names: `example-org/webapp`, `acme/app`, the workspace `C:/work/fleet`, the user `someone`. The scan `.github/scripts/private-names.mjs` lists the refused names and runs as the `R203` tests, so a leak fails the suite and CI. A fixture recorded live (a probe's events, a reply from GitHub) gets the same renames before it is committed. The leak guard refuses them in every tracked file of this repository, the wiki included, except its own files and the scan's (see "No machine paths and no private names").
- The scan reads source text line by line. It cannot see a name built at run time (`join`, `String.fromCharCode`), so a reviewer still reads each new fixture and path. Observed on #141: `test/trust.test.mjs` built a checkout path with `join`, and only a broader grep found it. A pattern for a path separator uses `[\\/]+`, because JS and JSON source write a backslash twice. The grep in #141 matched one backslash, so it missed every checkout-path literal written with doubled backslashes and undercounted the leaks.
- The scan lists its files with `git ls-files`, so it skips a file that is not yet tracked, and its summary does not say so. Stage a new file before you scan it, and check that the `files scanned` count went up by one. Observed 2026-11-22 on #210: the scan of a new page counted `124 files scanned` before `git add`, the same count as without the page, and `125 files scanned` once the page was tracked.
- A fake returns GitHub's real reply shape, errors included. Before you write a fake for a reply you have not seen, read that reply once live, with a read-only query. Observed 2026-11-12 on #108: the fake answered a missing project field with `field: null`, while GitHub returns a `NOT_FOUND` error. The tests passed, and sync would have failed on both real projects. A read-only survey caught it.
- The same holds at the `claude` boundary: a fake of `claude rm`, `claude --bg` or `claude stop` returns the text that `claude` prints, refusals included. Copy it from a probe's findings (the workspace repository's `probes/`) or a live run. Observed 2026-11-19 in the triage of #167: the real unpushed refusal starts with "kept <id>", which `HALF_FAILED_TEXT` in `plugin/cli/lib/worktrees.mjs` reads as a held folder. The fakes of R119 and R133 use a text without "kept", so they reach the `refused` branch and no test covers the path that the real text takes.
- Run `git` tests on local temporary repositories, never on one of the user's own checkouts.
- The unit tests of a helper get their own requirement prefix. They never share the prefix of an acceptance row that counts tests through the runner. On 2026-11-05 the unit tests of `dropBranch` were planned under `R105:` and would have counted toward a row that pledged five wrap-up tests. They use `R112:` instead. A row that counts exactly the helper's own prefix is fine: on 2026-11-06 AC1 of #32 counted the `R125:` helper tests and nothing else. The defect is a count that mixes prefixes.
- A `git cherry-pick` in a sandbox test can give the same commit hash as the original: the tree, the parent, the message and the second are the same. The picked commit then counts as pushed. Use `git cherry-pick -n` and commit with a new message. Observed 2026-11-10 on #70: an R175 test failed once in the full suite and once alone.
- In a `--require-merged` or `wrap` test, a fake merged pull request carries `head.sha`, `merged_at` and `base: { ref: 'main' }`, and the call passes `defaultBranch: 'main'`. The merge proof counts a pull request only when its `base.ref` is the default branch (rule 7 of `decideProof` in `plugin/cli/lib/merge-proof.mjs`), and proves nothing when the default branch is unknown. A plain-mode fake can leave `base` out, because the unpushed waivers in `safetyCheck` accept any base. Observed 2026-11-11 on #53: rule 7 turned 18 existing tests red on their fakes alone.
- Date the sandbox claim before any merge time it is compared with. With no issue branch left, `wrap` counts a closing pull request only when it merged at or after the claim's `claimedAt`. The `wrap` sandbox (`wrapSetup` in `test/helpers/wrap-shared.mjs`) dates its claim `CLAIMED_AT`, before `MERGED_AT`. The shared `setup` in `test/helpers/worktree-sandbox.mjs` dates it `NOW`, which is after `MERGED_AT`. Observed 2026-11-11 on #53.
- In a `wrap` test of an issue branch with commits of its own, the fake merged pull request at the tip is also a closing pull request of the issue: use `closingAtTip(s)` from `test/helpers/wrap-shared.mjs`, or list it in `closingPrs` or in the live read of the closing pull requests. A pull request found by head branch alone does not prove the work (`requireClosing` in `decideProof`). A closed issue can still pass on the nothing-to-lose proof (decision record 0016). Observed 2026-11-16 on #128: 13 fixtures had set the pull request by head branch only, and they passed only because the old rule was too weak.
- `runScript` in `test/helpers/run-script.mjs` returns `stdout` and `stderr` as Buffers, not strings. `assert.equal(r.stdout, '')` fails on an empty Buffer; compare `r.stdout.length` or `r.stdout.toString()`. Observed 2026-11-20 on #157.
- A test that runs the CLI passes `--workspace <sandbox>` or `cwd: <sandbox>`, never the repository checkout. With no `--workspace`, the CLI finds the workspace from its own folder, then from the current folder (decision record 0021). `plugin/cli/` holds no `config/`, so the CLI takes the outermost workspace at or above the current folder: in a worktree of this repository that is the live workspace, and in CI there is none, so the CLI exits 64. A command that exits 64 for its own reason can then pass for the wrong one. `runScript` and `spawnSync` take `cwd`. Observed on #82: four imported tests ran `ready`, `why`, `check-config` or the gvt-dev checks with neither flag.
- The `timeout` option of `node:test` cannot stop a synchronous infinite loop: the whole suite hangs. A test for code that could loop runs that code in a child process with `spawnSync(process.execPath, [...], { timeout })` and asserts the exit status.
- `plugin/hooks/hooks.json` is committed. `R216` in `test/plugin-hooks-json.test.mjs` checks that it equals `pluginHooksJson` of `plugin/cli/lib/user-settings.mjs` for the plugin's hook command. A change to the hook events, the matcher or the timeouts regenerates the file in the same commit.

## Windows rules the code depends on

- Use `py` for Python. `python3` is a Microsoft Store stub that exits 0 without running the script.
- Resolve every executable to an absolute path (PATH x PATHEXT) before spawning. A bare name can pick `System32` (for example `tar`), and `.cmd` shims such as `npm` fail without `PATHEXT`. Spawn with an argv array and no shell.
- Start a `.cmd` or `.bat` only through `cmdShimSpawn` in `plugin/cli/lib/proc.mjs`. It runs `cmd.exe /d /s /c` with the whole line in one extra pair of quotes and `windowsVerbatimArguments: true`. With node's default quoting, `/s` strips the quotes around the path, so a path with a space fails with "is not recognized" (measured 2026-11-04 on #9).
- `fs.existsSync` returns false for a dangling symbolic link. To decide that a file is missing, call `fs.lstatSync` and test for ENOENT.
- Keys in `~/.claude.json` use forward slashes and an uppercase drive letter.
- Write generated files with LF line endings and a trailing newline.
- Take a script's own path from `fileURLToPath(import.meta.url)`, not from `URL.pathname`.
- Base clones use HTTPS, not SSH. SSH needs a 1Password approval for each signature. HTTPS authenticates through Git Credential Manager (`credential.helper=manager`). Every git call sets `GIT_TERMINAL_PROMPT=0`, so a missing credential fails at once instead of waiting for a prompt. Checked 2026-11-03: a clone and a fetch of a private managed repository finished with rc=0 and no prompt.
- End a child process that has a time limit by killing its process tree (`taskkill /T`, run by absolute path), and return the result without waiting for `close`. A git helper (`git-remote-https`) keeps the stdio pipes open after git itself is killed, so a runner that waits for `close` never returns. `run` in `plugin/cli/lib/proc.mjs` does this. Measured 2026-11-05: before the fix, `git ls-remote` against a local server that never answers was still pending at 15 s with a 3 s limit. The holder lookups had the same flaw. A test of such code runs the hang in a child process with a bounded `spawnSync` (see "Test conventions").
- A `run` call with `timeoutMs: N` returns after N ms plus up to about 8 s: `taskkill` runs synchronously for up to 5 s, then a 3 s grace wait. Only Windows kills the whole tree; elsewhere `run` kills the child only. A doc or HELP sentence about a time limit states both facts. Observed 2026-11-09 on #52: the docs said "the process tree is killed" after 30 s, and the review corrected both points.
- Each base clone keeps `/.claude/worktrees/` in `.git/info/exclude`. Without that line, a nested worktree at `.claude/worktrees/<name>` makes `git status --porcelain` in the base clone list `.claude/`, and `clone` then skips the base clone as dirty. `clone` adds the line on every run.
- A recursive delete (`fs.rmSync`) that fails on a held folder can remove the `.git` file first and leave the folder. Measured 2026-11-09 on #60: a child process with its current folder there gave EPERM, and the folder was left empty. `git worktree list --porcelain` then still lists the entry (through the renamed `<name>.claude-dropped-*` admin dir), with a `prunable` line. `observe` in `plugin/cli/lib/worktrees.mjs` counts a folder with no `.git` entry that git marks `prunable` as not listed; when that folder is empty, the removal retry deletes it. Code that retries after a failed delete must handle this state.

## Safety rules for the code and its probes

- In `safetyCheck` (`plugin/cli/lib/worktrees.mjs`), a pull request list waives only the branch it was looked up for. The pull requests found by commit waive HEAD only. `found` (the issue branch's own and the closing pull requests) waives the issue tip. Pooling them lets another branch's pull request stand in for the issue branch, which decision record 0011 forbids. Found in the code review of #70 (2026-11-10).
- A probe that starts `claude --bg` in a sandbox needs a trust entry for that exact folder. A trusted parent folder does not count, and `claude --bg` exits 1 with `Workspace not trusted`. Put the sandbox under `<workspace>/repos/probe/` and run `gvt-fleet trust <sandbox base>` for each base folder (observed 2026-11-06, #38), with the CLI of the workspace's main checkout: `node <workspace>/bin/gvt-fleet.mjs trust <sandbox base>`. A worktree's CLI took the worktree as its workspace and refused the sandbox with exit 2 (`outside workspace`; observed 2026-11-08, #34). No command removes a trust entry, so the entry of a deleted sandbox stays in `~/.claude.json`.
- A probe of the order of hook events registers every event that can come between the records it draws a conclusion from, not only the events under study. Build the probe settings from the branch's own `planSettings` output, with all the hook events, and point the commands at a scratch `--state-dir`. Then read the session transcript (its `tool_result` lines) to see what happened between the records. A question that a probe asks with `AskUserQuestion` can be answered from outside the session. Observed 2026-11-13 on #105: a probe with only `PreToolUse` and `Notification` hooks showed `PreToolUse`, `permission_prompt`, `idle_prompt`. The question had been answered, and the turn had ended with a `Stop` that the probe did not record. The wrong order reached the issue, decision record 0017, a test and the docs before the live worker file showed the `Stop`.
- A probe of hook behaviour in a headless session (`claude -p`) passes `--setting-sources project,local` and puts its own hooks in the sandbox's `.claude/settings.json` or in a `--plugin-dir` plugin. The user-scope `gvt-fleet` hook then stays off, and the probe writes nothing to the workspace's `state/workers/`. Write each command of its prompt as `node <script>`, with the bare name. `--allowedTools "Bash(node:*)"` does not match a command that starts with the quoted absolute path of `node.exe`, and the session stops with "This command requires approval"; the `permission_denials` of its JSON output names the call. Observed 2026-11-25 on workspace #178: the first run of the hook-reload probe stopped at its first command.
- Tests make no live GitHub writes. Read-only live runs are done by hand, never by a test.
- An `updateProjectV2Field` call that changes the options of a single-select field passes the `id` of every existing option. With the ids, item values are kept, also when a description changes or an option is added. Without them, GitHub replaces the options and every item's value is cleared (#95). The same holds for the iterations of an Iteration field: an existing iteration whose `id` is left out is replaced, and its items lose their value. Probed 2026-11-12 on a throwaway project (#108). Record the old values in a file before any such write, in case an id is missing.
- An Iteration field update has one `iterations` list, and it must also carry the completed iterations (read from `completedIterations`). A completed iteration left out is deleted, and its items lose their value. An iteration that overlaps another is dropped with no error. So lay iterations out back to back, and read the field back after every write. `plugin/cli/lib/projects.mjs` does this (decision record 0015). Probed 2026-11-12 on a throwaway project (#108).
- An iteration of zero days is refused (`UNPROCESSABLE`, "Settings completed iterations duration must be greater than 0"), and nothing is written. Two iterations with the same start date overlap: the update is accepted, one of them is dropped with no error, and its items lose their value. The start date and duration of a completed iteration can be changed, with every id passed, and its items keep their value. A gap between iterations is kept. So every layout gives each iteration at least one day, and `assertValidLayout` in `plugin/cli/lib/iterations.mjs` checks that and the overlap before each write (decision record 0022). The fake project in `test/fakes/fake-project.mjs` refuses and drops the same way. Probed 2026-11-22 on a throwaway user-owned project (#202): `createProjectV2` with the viewer's id, draft items with `addProjectV2DraftIssue`, and `deleteProjectV2` afterwards ran in a background job with no refusal.
- `field(name: …)` for a field that the project does not have returns a `NOT_FOUND` error on the path `…projectV2.field`, and the rest of the data. It does not return `null`. An item's `fieldValueByName` for that field returns `null` with no error. Both read live on 2026-11-12 (#108).
- An issue's `projectItems` and `projectsV2` list only the items of projects owned by the repository's owner. A cross-organization item is missing, and the same token reads it from the project side. Find such an item with `items(query: "repo:<owner/name>")` on the project, and read one item by id with `node(id:)`. Read live on 2026-11-16 (#143, decision record 0018). The `items(query:)` search can miss an item that was added minutes earlier, so read a just-added item back by id. Observed 2026-11-18 on #162: right after the "Set road block" recipe added the item, the search returned 62 items without it and `items(last: 10)` did not list it, while `node(id:)` showed the value. Some minutes later the search returned 63 items, #162 included.
- Only `gvt-fleet install-hooks` writes `~/.claude/settings.json`. Tests inject the settings path and never touch the real file.
