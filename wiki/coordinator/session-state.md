# Commands: session state

This page is part of the [gvt-fleet command reference](../coordinator.md).

The session hooks record the state of each worker session under `state/workers/`. The status-line helper records the account-wide rate limits in `state/rate-limits.json`. Until the `gvt-fleet` plugin ships its hooks, both are registered in the user settings ([ADR 0003](../decisions/0003-register-session-hooks-at-user-scope.md)).

## gvt-fleet install-hooks

```
gvt-fleet install-hooks [--dry-run]
```

Registers the session hooks and the status line in `~/.claude/settings.json`.

It works in one of two modes ([ADR 0021](../decisions/0021-find-the-workspace-and-switch-the-hooks-to-the-plugin.md)). It reads `~/.claude/plugins/installed_plugins.json` and takes the `gvt-fleet@gvt-plugins` install of scope `user`, else the first one listed.

- **Plugin mode**, when that install folder has `cli/bin/gvt-fleet-hook.mjs` and `hooks/hooks.json`. The plugin runs the hooks, so `install-hooks` removes every hook entry of ours from the settings, one change line `hooks.<Event>: remove our entry (the gvt-fleet plugin runs the hook)` per event; an event left with no group loses its key. It writes the launcher `gvt-fleet-statusline-launcher.mjs` into the plugin data folder (`CLAUDE_PLUGIN_DATA` when set, else `~/.claude/plugins/data/gvt-fleet-gvt-plugins/`), with the change line `launcher: write <path>`, before it writes the settings. It sets `statusLine` to `node "<launcher>" --workspace "<workspace>"`, with `--state-dir` and `--chain` as below. On each render, the launcher finds the current install folder in `installed_plugins.json` and runs that copy's `cli/bin/gvt-fleet-statusline.mjs` with the same arguments, so a plugin update does not move the status line. When it finds no copy, it runs the command after `--chain` itself, so the status line still shows, and no limits are recorded. A launcher whose bytes differ from the current one is rewritten.
- **User-settings mode**, otherwise: the entries below, which name the scripts in the `bin/` folder of the CLI that runs `install-hooks`, and the workspace after `--workspace`. The two folders differ when the CLI does not sit in the workspace. Going back from plugin mode (an older plugin release installed again) writes these entries again.

In user-settings mode:

- It adds six hook entries, for `SessionStart`, `Notification`, `Stop`, `StopFailure`, `SessionEnd` and `PreToolUse`. The `PreToolUse` entry is in a group with the matcher `AskUserQuestion` and has timeout 10, so it runs only on an `AskUserQuestion` call. An entry of ours found in a `PreToolUse` group with another matcher, or with no matcher, is moved to a group with the matcher `AskUserQuestion`, or dropped when such a group already holds our entry; the other entries of that group stay. Each entry runs `<CLI folder>/bin/gvt-fleet-hook.mjs` with the workspace root as `--workspace`. When the global `--state-dir` names a folder other than `state/` at the workspace root, the installed hook and status-line commands pass it on as `--state-dir "<folder>"`, so the hooks, the status-line helper and the backup all use that folder.
- It sets `statusLine` to run `bin/gvt-fleet-statusline.mjs`. When a status-line command already exists, the new command runs the helper and passes the existing command after `--chain`. The helper first reads its stdin, for at most 2 seconds. It then runs the existing command with that input.
- Existing hooks and other keys are kept. The file is parsed and rewritten as JSON. A rewrite would drop all but the last value of a duplicate key, and would change a number that a double cannot hold exactly (for example `12345678901234567890`, `1e400` or `-0`). So it refuses and writes nothing when the file has a duplicate key or a number that would change; the reason names the key or the number and its line. The backup keeps the original bytes.
- On a re-run, its own entries are updated in place, and nothing is added twice. An entry is its own only when its whole command has the form that install-hooks writes: `node "<path>/bin/gvt-fleet-hook.mjs" --workspace "<path>"` for a hook, or `node "<path>/bin/gvt-fleet-statusline.mjs" --workspace "<path>"` or `node "<path>/gvt-fleet-statusline-launcher.mjs" --workspace "<path>"` for the status line. The script folder and the workspace may be different paths. An optional `--state-dir "<folder>"` (and, for the status line, `--chain <command>`) follows. An entry pointing at an older workspace or script folder still counts, so a moved workspace is updated in place. A user command that only mentions one of the script names is left alone. A run with nothing to change prints `noop`.
- An entry written under the old script names (`gvt-loop-hook.mjs`, `gvt-loop-statusline.mjs`) counts as its own and is replaced in place. The change lines are `hooks.<Event>: rename our entry from gvt-loop-hook.mjs to gvt-fleet-hook.mjs` and `statusLine: rename our command from gvt-loop-statusline.mjs to gvt-fleet-statusline.mjs`. The old names are only recognised, never written. See [Moving from the gvt-loop names](moving-from-gvt-loop-names.md#moving-from-the-gvt-loop-names).
- When the status-line command holds our helper inside our helper (a nested chain), the change is `statusLine: unwrap a nested status-line helper`. When an event holds more than one entry of ours, it keeps the first and removes the others; each removal is `hooks.<Event>: remove a duplicate of our entry`. A group left with no entry is removed.
- The first run that writes records how to undo it, once. When the settings file exists, it copies the original to `state/settings.json.bak`. When the file is missing, it creates the file and writes `state/settings.json.absent` instead. When the file already holds our entries (under the old or the new script names) and `state/` has neither record (for example after `state/` was deleted), it takes no backup, because the copy would hold our hooks, and it reports `backup: none taken, the file already holds our entries`. Once either record exists, a later run never replaces it and adds no other record.
- After a write, it waits 3 seconds and reads the file again, because Claude Code can overwrite the file. It plans the changes again and writes again if any are missing, up to 3 attempts in all. If they are still missing, the result is `failed`.
- It refuses and writes nothing when the file is not valid JSON, when the file starts with a UTF-8 byte order mark (the reason names it; save the file as UTF-8 without a BOM), when `statusLine` is not a command, when the existing status-line command contains a shell operator, when the status-line command to chain starts a batch file (its first word resolves to a `.cmd` or `.bat` on `PATH`) and an argument, as written, has a character other than letters, digits and `_ . / : @ # = -` (the helper does not pass such an argument to a batch file, so the status line would go blank; the reason names the argument; one pair of quotes around an otherwise plain argument is allowed), when that batch file's resolved path contains `"` or `%` (the helper does not run such a path), or when one of the six hook events (`PreToolUse` included) is not a list. It also refuses when the file is not a JSON object or `hooks` is not an object.
- `--dry-run` prints the changes and the result. It writes nothing to the settings file and takes no backup; it only writes to `state/gvt-fleet.log.jsonl`, as every run does: its result line and, on the first write, the log rename and its `log-renamed` line (see [Where state lives](../coordinator.md#where-state-lives)).
- Output is one line per change, then `<settings path>: <status>`. The status is `written`, `noop`, `dry-run`, `refused` or `failed`. With `--json`, it prints one object, `{ path, status, changes, reason? }`. A refusal or a failure also prints `<path>: <status>: <reason>` on stderr.
- Open sessions may keep the hooks and status line it read at start, so restart them after the install. An install made before the `PreToolUse` entry existed gets that entry only when `install-hooks` runs again.
- Side effects: it rewrites `~/.claude/settings.json` (keeping the key order) and writes the backup. When the settings file is a symbolic link, the change is written through the link to its target. From then on, every Claude Code session on the machine runs the hook script on the first five events, and on an `AskUserQuestion` call for the sixth, and every status-line render runs the helper first. The hook script records state only for a session whose `cwd` is at or below a worktree root under this workspace's `repos/`.
- Exit codes: 0 for `written`, `noop` or `dry-run`, 1 for `failed`, 2 for `refused`, 64 for a wrong argument.

**What runs afterwards.** The hook script reads the event from stdin. When the `cwd` is not at or below a worktree root under `repos/`, it does nothing.

**The hook without `--workspace`.** The plugin's `hooks.json` runs the hook with no workspace ([ADR 0021](../decisions/0021-find-the-workspace-and-switch-the-hooks-to-the-plugin.md)). The hook then works out the workspace from the session folder: each `<W>` such that the `cwd` is at or below `<W>/repos/<owner>/<repo>/.claude/worktrees/<name>` is a candidate, tried from the innermost. The first candidate that holds `config/repos.json` as a file is the workspace, and the record goes to `<W>/state/`, or to the folder that `--state-dir` names. A `cwd` of no such shape reads no file and writes nothing; a candidate with no `config/repos.json` is skipped. With `--workspace`, as in the entries that `install-hooks` writes, the hook uses that workspace as before. A `cwd` that has a `.` or `..` segment anywhere in it is treated the same way: such a segment is out of scope, because joining it into a path could place the record outside `state/workers/`. Otherwise it appends one line to `state/workers/<owner>/<name>/<worktree>.jsonl`. A `PreToolUse` record keeps `tool_name` and `tool_use_id`. For `AskUserQuestion` only, it also keeps `questions`, a list of `{question, header, options, multiSelect}` where `options` lists the option labels, capped at 4 questions, 6 options, 600 characters for a question, 60 for a header and 120 for a label. Trailing questions are dropped until the list takes at most 6000 bytes, so the record stays under its 8 KB line cap. It does not keep `tool_input` in `extra`. An unexpected error goes to `state/hook-errors.jsonl`. The script prints nothing and always exits 0, so it cannot change the flow of a session. The helper reads its stdin first, for at most 2 seconds, and keeps what it read. It then starts the existing status-line command with that input and shows that command's output unchanged. When that command is a `.cmd` or `.bat` file, the helper runs it through `cmd.exe` with the whole path in quotes, so a path with a space works (for example `npx.cmd` under `C:\Program Files\nodejs`); a path that contains `"` or `%` is not run. It records the rate limits while the command runs, and a failure to record does not change the display. A payload without `rate_limits` leaves the snapshot as it was.
